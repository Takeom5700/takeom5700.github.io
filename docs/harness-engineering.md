# ハーネスエンジニアリング入門（練習用ノート）

このリポジトリ（`takeom5700.github.io`）を題材に、**ハーネスエンジニアリング**の考え方と書き方を
一通り練習するためのノートです。読むだけでなく、末尾の「練習課題」を上から順にやると身につきます。

> このドキュメントは解説専用です。読んでも設定は変わりません。
> 実際に `.claude/` を作るのは練習課題のステップです。

---

## 1. ハーネスとは何か

「ハーネス（harness）」は本来「馬具」「配線束」の意味で、**中身そのものではなく、中身を正しく働かせるための外側の仕組み**を指します。
AI エージェント開発では、次のように分けて考えます。

| | 何か | 誰が決めるか | 変えると何が起きるか |
|---|---|---|---|
| **モデル** | 推論する本体（Claude 本体） | 提供側 | 賢さ・速度が変わる |
| **ハーネス** | モデルに渡す文脈・使える道具・実行ルール・自動化 | **あなた** | 同じモデルでも成果物の質と再現性が変わる |

同じモデルでも、ハーネスが違えば結果は大きく変わります。
ハーネスエンジニアリングとは、**「毎回同じ説明をしなくても、エージェントが正しく動く状態」を設計・実装する仕事**です。

判断基準はシンプルです:

> 同じ指示を 3 回出して、3 回とも同じ品質で返ってくるか？
> 返ってこないなら、それはプロンプトの問題ではなくハーネスの不足です。

---

## 2. ハーネスの部品と置き場所

Claude Code のハーネスは、おおむね次の 7 つの部品でできています。

| 部品 | 置き場所 | いつ読まれるか | 性質 |
|---|---|---|---|
| **プロジェクトメモリ** | `CLAUDE.md`（リポジトリ直下） | 毎セッションの最初に**常時** | 常時コスト |
| **設定 / 権限** | `.claude/settings.json` | セッション開始時 | 決定論的 |
| **フック** | `.claude/settings.json` の `hooks` | 指定イベント時に**必ず**実行 | 決定論的 |
| **スラッシュコマンド** | `.claude/commands/<名前>.md` | ユーザーが `/名前` と打った時 | 明示的 |
| **スキル** | `.claude/skills/<名前>/SKILL.md` | モデルが必要と判断した時 | 自律的 |
| **サブエージェント** | `.claude/agents/<名前>.md` | 別コンテキストで仕事を委譲する時 | 分離的 |
| **MCP サーバー** | `.mcp.json` | 外部ツールを繋ぐ時 | 外部接続 |

さらにリポジトリ側の CI（このリポジトリなら `.github/workflows/ai-shinbun.yml`）も、
「人の介在なしにエージェントを走らせるハーネス」です。ローカルのハーネスと地続きに考えます。

## 3. どれを使うか：判断フロー

新しく「エージェントにこうしてほしい」と思ったとき、次の順で考えます。
**上にあるものほど安く、確実です。**

```
その要求は…
├─ 例外なく毎回必ず実行されるべきか？
│   └─ YES → フック（Hook）
│            例: 保存したら必ずフォーマッタを走らせる
│                危険なコマンドを必ず止める
│
├─ 人が「今これをやって」と明示的に起動するか？
│   └─ YES → スラッシュコマンド
│            例: /new-column 記事タイトル
│
├─ 状況に応じてモデルが自分で「使うべきだ」と気づくべきか？
│   └─ YES → スキル
│            例: 新聞ページを触るときだけ組版ルールを読み込む
│
├─ 大量の探索が必要で、その中間結果は本体の文脈に要らないか？
│   └─ YES → サブエージェント
│            例: 全ファイルから命名規約の揺れを洗い出す
│
├─ 外部サービス（API・DB・SaaS）に触る必要があるか？
│   └─ YES → MCP サーバー
│
└─ どのタスクでも共通に効く短い前提知識か？
    └─ YES → CLAUDE.md（ただし短く！ 4 章参照）
```

**よくある間違い**は、全部を `CLAUDE.md` に書いてしまうことです。
`CLAUDE.md` は毎回全文が文脈に載るので、長くなるほど 1 行あたりの効き目が薄まります。

## 4. 各部品の書き方

### 4.1 CLAUDE.md — 「常時ロードされる短い前提」

**入れるもの**（そのリポジトリで作業する人が、初日に必ず知るべきこと）:

- ディレクトリの意味（何がどこにあるか、生成物はどれか）
- 触ってはいけないファイル / 自動生成ファイル
- ビルド・確認コマンド（あるなら）
- このプロジェクト固有の約束事（言語、日付形式、コミットの粒度）

**入れないもの**:

- 一般的なプログラミング作法（モデルは既に知っています）
- ごく一部のタスクでしか使わない長い手順（→ スキルへ）
- 変わりやすい TODO やメモ（すぐ古くなり、嘘の文脈になります）

**目安は 50〜150 行**。これを超えたら、そのブロックはスキルに切り出すサインです。

書き方の例（このリポジトリを想定した骨子）:

```markdown
# takeom5700.github.io

GitHub Pages で配信する静的サイト。ビルド工程はなく、HTML をそのまま配信する。

## 構成
- `index.html` — ポータル本体（単一ファイル、約 116KB。CSS/JS を内包）
- `ai-shinbun/` — 毎日 GitHub Actions が生成する AI 新聞。**手で編集しない**
- `uranai/`, `mistlands/` — 個別コンテンツ（それぞれ独立した単一 HTML）
- `.github/scripts/generate_newspaper.py` — 新聞生成スクリプト（Gemini API）
- `sw.js` — Service Worker。`CACHE_NAME` の版数で配信キャッシュを切る

## 約束事
- 表示テキストは日本語。日付は JST。
- 配信ファイルを変更したら `sw.js` の `CACHE_NAME` を必ず 1 上げる。
- 新規の公開ページを足したら `sitemap.xml` にも追記する。
```

> ポイント: 「`sw.js` の版数を上げる」のような**忘れると壊れるルール**は、
> CLAUDE.md に書くだけでは 100% にはなりません。確実にしたいならフックにします（4.3）。

### 4.2 settings.json — 権限とプロジェクト設定

`.claude/settings.json` はリポジトリにコミットする共有設定、
`.claude/settings.local.json` は個人用（`.gitignore` 対象）です。

```json
{
  "permissions": {
    "allow": [
      "Bash(python .github/scripts/generate_newspaper.py)",
      "Bash(git status:*)",
      "Bash(git diff:*)"
    ],
    "deny": [
      "Bash(git push:*)",
      "Read(./.env)"
    ]
  },
  "env": {
    "TZ": "Asia/Tokyo"
  }
}
```

設計の勘所:

- `allow` は**確認を毎回聞かれてうっとうしい読み取り系**から埋めていく。
- `deny` は**取り返しがつかない操作**に使う（push、削除、外部送信）。
- 「危ないから全部聞く」は一見安全ですが、確認疲れで人が中身を読まずに承認するようになります。
  安全なものを明示的に通し、危ないものだけ止めるほうが、実際には安全になります。

### 4.3 フック — 「必ず起きること」を確定させる

プロンプトやメモリは**確率的**です（だいたい守られる）。
フックは**決定論的**です（必ず実行される）。
「忘れられたら困ること」は、必ずフックにします。

主なイベント:

| イベント | タイミング | よくある用途 |
|---|---|---|
| `SessionStart` | セッション開始時 | 依存インストール、環境情報を文脈に注入 |
| `UserPromptSubmit` | ユーザー送信直後 | 追加文脈の注入、危険な入力の遮断 |
| `PreToolUse` | ツール実行**前** | 危険コマンドのブロック、対象の検証 |
| `PostToolUse` | ツール実行**後** | フォーマッタ、リンタ、整合性チェック |
| `Stop` | 応答終了時 | 完了条件の検査、通知 |

設定の形（`matcher` はツール名、複数のフックを並べられます）:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/check-cache-version.sh" }
        ]
      }
    ]
  }
}
```

フックスクリプトは **stdin から JSON** を受け取ります
（`session_id` / `cwd` / `hook_event_name` / `tool_name` / `tool_input` など）。
終了コードの意味が重要です:

- `0` — 正常。標準出力はログとして扱われる（`SessionStart` / `UserPromptSubmit` では**文脈に追加**される）
- `2` — **ブロック**。標準エラー出力の内容が Claude に返され、Claude はそれを読んで修正を試みる
- その他 — 非致命的エラーとして扱われる

このリポジトリ向けの実例（配信ファイルを触ったのに `sw.js` の版数が据え置きなら警告する）:

```bash
#!/usr/bin/env bash
# .claude/hooks/check-cache-version.sh
set -euo pipefail

changed=$(git diff --name-only -- '*.html' 'manifest.json' | grep -v '^ai-shinbun/' || true)
[ -z "$changed" ] && exit 0

if git diff --quiet -- sw.js; then
  echo "配信HTMLを変更していますが sw.js の CACHE_NAME が未更新です: $changed" >&2
  exit 2   # ← Claude に差し戻して直させる
fi
```

**フック設計の原則**

1. **速いこと。** 毎回走るので、数百ミリ秒を超えると体感が悪化します。
2. **冪等であること。** 同じ状態で二度走っても壊れない。
3. **失敗メッセージが行動可能であること。**
   「エラー」ではなく「`sw.js` の `CACHE_NAME` を v35 → v36 に上げてください」と書く。
   フックの出力は**モデルへの指示**です。人向けのログではありません。
4. **黙って直すか、止めて言うか、決める。**
   フォーマッタは黙って直す。設計判断が要るものは `exit 2` で止めて説明する。

### 4.4 スラッシュコマンド — 「人が起動する定型作業」

`.claude/commands/new-column.md` を置くと `/new-column` で呼べます。

```markdown
---
description: 新しいコラムページの雛形を作る
argument-hint: <slug> <タイトル>
allowed-tools: Read, Write, Bash(git status:*)
---

`column-tips.html` を雛形として `column-$1.html` を作成する。

手順:
1. `column-tips.html` を読み、構造（head のメタ、ヘッダー、フッター）を把握する
2. 本文を空にし、タイトルを「$2」に差し替えた `column-$1.html` を作る
3. `sitemap.xml` に `<loc>https://takeom5700.github.io/column-$1.html</loc>` を追記する
4. `sw.js` の `CACHE_NAME` の版数を 1 上げる
5. 変更したファイルの一覧を報告する（コミットはしない）
```

- `$1`, `$2` … 位置引数。`$ARGUMENTS` は全引数。
- 本文中で `@ファイル名` と書くとそのファイルを参照させられます。
- `allowed-tools` を絞ると、そのコマンドの実行中に事故が起きにくくなります。

**コマンドは「手順書」です。**「よしなにやって」ではなく、番号付きの手順で書く。
迷いどころ（例: sitemap を更新するか）を手順に明記しておくのが価値の中心です。

### 4.5 スキル — 「必要なときだけ開く専門知識」

スキルは `.claude/skills/<名前>/SKILL.md` に置きます。
スラッシュコマンドとの違いは、**モデルが自分で「今これが要る」と判断して読む**点です。

```markdown
---
name: newspaper-page
description: ai-shinbun/ の新聞HTMLを生成・修正・検証するときに使う。組版ルール、
  テンプレート変数、バックナンバー一覧への追加手順を含む。新聞、縮刷版、
  newspaper_YYYYMMDD.html に触れる作業で必ず適用する。
---

# AI新聞ページの作法

## テンプレート
`.github/scripts/newspaper_template.html` が唯一の正。直接 HTML を書き起こさない。
`{{YEAR}}` `{{MONTH}}` `{{DAY}}` が置換対象。

## 生成後に必ず確認すること
1. ファイル名が `ai-shinbun/newspaper_YYYYMMDD.html` 形式か
2. `ai-shinbun/index.html` のカード一覧に新しい号へのリンクが**先頭に**追加されているか
3. ダークモード（`prefers-color-scheme: dark`）の変数定義が欠けていないか

## 詳細
組版の詳細ルールは `references/typography.md` を参照（必要になったときだけ読む）。
```

**description がスキルの心臓部**です。ここだけが常時ロードされ、
モデルはこの一文だけを見て「開くかどうか」を決めます。したがって:

- **何をするか** と **いつ使うか** の両方を書く
- 実際に本文中に出現する語（`newspaper`, `縮刷版`, ファイル名パターン）を含める
- 「役に立ちます」ではなく「〜のときに使う」と条件を書く

**段階的開示（progressive disclosure）** が設計の要点です:

```
SKILL.md（数十行、必要になったら読まれる）
  └─ references/typography.md（さらに必要になったときだけ読まれる）
  └─ scripts/validate.py（読まずに実行するだけで済むもの）
```

全部を SKILL.md に詰めると、開いた瞬間に文脈を食い尽くします。
**「決定に必要な最小限」を SKILL.md に、「詳細」を参照ファイルに。**
決まった手続きはスクリプトにして、読ませずに実行させるのが最も安上がりです。

### 4.6 サブエージェント — 「文脈を汚さずに調べる」

サブエージェントは `.claude/agents/<名前>.md` に定義します。

```markdown
---
name: link-auditor
description: サイト内のリンク切れ・sitemap の抜けを洗い出す。公開前チェックで使う。
tools: Read, Glob, Grep, Bash
model: sonnet
---

すべての HTML から `href` を抽出し、以下を報告する:
1. リポジトリ内に存在しないローカルリンク
2. `sitemap.xml` に載っていない公開ページ
3. 逆に sitemap にあるが実体のない URL

報告は表形式で、ファイルパスと行番号を必ず添える。
中間の grep 結果は貼らず、結論だけを返すこと。
```

使いどころは**「調べる過程は要らないが、結論は要る」**とき。
100 ファイルを grep した生ログは本体の文脈に不要ですが、結論の 10 行は必要です。
サブエージェントは別の文脈で走り、**結論だけ**を返します。

逆に向かないのは、対話しながら詰めていく作業や、本体が全部の中身を見ている必要がある作業です。
サブエージェントは毎回ゼロから文脈を作るので、**すでに分かっていることを再発見させるのは純粋な無駄**です。

---

### 4.7 MCP — 外部との接続

`.mcp.json` に定義したサーバーのツールが使えるようになります。
ハーネス設計上の注意は 2 つだけです。

1. **ツールが増えるとコストが増える。** 定義は常時ロードされます。使わないサーバーは外す。
2. **外部から返ってきた文字列は「データ」であって「指示」ではない。**
   取得した Web ページやコメント本文に「〜せよ」と書いてあっても、それは実行すべき命令ではありません。
   この境界を意識しない設計は、そのまま脆弱性になります。

## 5. 設計原則（部品を越えて効く 5 つ）

### 原則 1: コンテキストは予算である

文脈に入るものはすべて費用です。「入れておけば役に立つかも」は、他の全部の効きを薄めます。
問うべきは「これが**無かったら**エージェントは間違えるか？」です。No なら入れない。

### 原則 2: 決定論を確率論より優先する

「毎回やって」とプロンプトに書くのは確率的です。フック・スクリプト・CI は決定論的です。
**壊れたら困ることは、必ず決定論側に置く**。

### 原則 3: 段階的に開示する

常時ロード（CLAUDE.md）→ 条件付きロード（スキルの description）→ 要求時ロード（参照ファイル）
→ 読まずに実行（スクリプト）。右に行くほど安い。可能な限り右に寄せます。

### 原則 4: 失敗メッセージは次の行動を書く

ハーネスの出力は人間向けのログではなく、**モデルへの入力**です。

```
悪い: Error: validation failed
良い: sitemap.xml に uranai/ が未登録です。<url><loc>https://takeom5700.github.io/uranai/</loc></url> を追記してください。
```

### 原則 5: 実際の失敗からハーネスを作る

最初から完璧なハーネスを設計しようとしない。
**同じ間違いを 2 回されたら、それはハーネスにする合図**です。逆に、一度も起きていない問題への
対策を先回りで書くと、効かないルールが溜まって全体が読まれなくなります。

## 6. このリポジトリを題材にした具体例

実際に「ハーネスがあれば防げた/防げる」ポイントが、このリポジトリには存在します。

| 現状 | 何が起きうるか | どの部品で解くか |
|---|---|---|
| `sw.js` の `CACHE_NAME`（現在 `v35`）を手で上げている | 上げ忘れると古いページが配信され続ける | **PostToolUse フック**で HTML 変更時に検査 |
| `sitemap.xml` に `uranai/` と `ai-shinbun/` が未登録 | 新規ページを足すたび同じ抜けが再発する | **フック**（検査）＋ **スラッシュコマンド**（追加手順の定型化） |
| `ai-shinbun/index.html` のカード一覧を手で追記 | 新聞は自動生成なのに一覧だけ手作業でズレる | **スキル**（新聞作業時の手順）または生成スクリプト側で自動化 |
| `generate_newspaper.py` が API キー未設定で `exit 1` | CI が落ちた理由が分かりにくい | **CI 側のハーネス**：失敗理由を明示するメッセージ |
| `index.html` が 116KB の単一ファイル | 全文を読ませると文脈を大量に消費する | **サブエージェント**に探索を委譲、または CLAUDE.md に構造の地図を書く |

「ハーネスを作る」とは、こういう**再発する手作業と、忘れると壊れる約束**を
一つずつ機械に移す作業のことです。

## 7. 練習課題（この順にやると身につきます）

### Lv1 — CLAUDE.md を書く（30 分）
4.1 の骨子を参考に、このリポジトリの `CLAUDE.md` を **80 行以内**で書く。
書き終えたら 1 行ずつ「これが無かったらエージェントは間違えるか？」を問い、No の行を消す。
**評価**: 消せた行があるほど良い。

### Lv2 — スラッシュコマンドを 1 つ作る（30 分）
`/new-column <slug> <タイトル>` を作る（4.4 参照）。
**評価**: 手順の中に「sitemap も更新する」「`sw.js` の版数も上げる」が入っているか。
入っていなければ、それはあなたの頭の中にしかない知識です。

### Lv3 — フックを 1 つ作る（1 時間）
`PostToolUse` で `sw.js` の版数チェックを実装する（4.3 のスクリプト参照）。
**評価**: わざと HTML だけ編集して、**ちゃんと止まるか**を確認する。
止まらないハーネスは存在しないのと同じです。

### Lv4 — スキルを 1 つ作る（1〜2 時間）
`newspaper-page` スキルを作り、`SKILL.md` は 50 行以内、詳細は `references/` に分ける。
**評価**: 「新聞の 8/29 号を直して」とだけ言って、スキルが**自動で開かれるか**。
開かれなければ `description` の書き方の問題です（4.5 参照）。

### Lv5 — 壊してから直す（重要）
作ったハーネスを意図的にすり抜ける指示を出してみる。
- フックを回避できる編集経路はないか（`Bash` の `sed` 経由など）
- スキルが開かれない言い回しはないか
- コマンドの手順を飛ばしても完了報告されないか

**ハーネスの品質は、順調なときではなく、外れたときの挙動で決まります。**

## 8. よくある失敗

| 失敗 | なぜ起きるか | 直し方 |
|---|---|---|
| CLAUDE.md が 500 行 | 「書いておけば守られる」と思っている | 条件付きの知識をスキルへ移す |
| スキルが発動しない | `description` が抽象的 | 「いつ使うか」と具体語を入れる |
| フックが遅くて邪魔 | 毎回フルビルドしている | 変更ファイルだけを対象にする |
| ルールが守られない | 確率的な場所（メモリ）に書いている | 決定論的な場所（フック/CI）へ移す |
| サブエージェントを乱発 | 「分ければ速い」と思っている | 既知の文脈を再発見させるだけなら自分でやる |
| 権限を全部 `ask` | 安全に見える | 承認が形骸化する。安全なものは通す |

## 9. レビュー用チェックリスト

自分の書いたハーネスを見直すときに使ってください。

- [ ] `CLAUDE.md` の各行は「無いと間違える」ものだけか
- [ ] 忘れると壊れるルールが、メモリではなくフック/CI にあるか
- [ ] スキルの `description` に「いつ使うか」が書いてあるか
- [ ] `SKILL.md` は決定に必要な最小限か（詳細は参照ファイルへ）
- [ ] 失敗メッセージが「次に何をすべきか」を書いているか
- [ ] フックは冪等で、十分に速いか
- [ ] 意図的にすり抜けようとしたとき、どこかで止まるか
- [ ] 誰も使っていない部品が残っていないか（未使用は削除する）
